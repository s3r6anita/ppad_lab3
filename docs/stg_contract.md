# Контракт STG: GitHub → DWH

Версия контракта: 1.

## Назначение

STG хранит исходные данные GitHub REST API и метаданные загрузки.
Нормализация, бизнес-фильтрация и SCD2 выполняются в DDS.

## Источники

Для каждого репозитория owner/repository:

- GET /repos/{owner}/{repo}
- GET /repos/{owner}/{repo}/issues

Список репозиториев будет храниться в config/repositories.json.

Изначальный состав:
- arkivanov/Decompose
- arkivanov/MVIKotlin
- arkivanov/Essenty

## Режим загрузки

Первая версия выполняет полную загрузку при каждом запуске.

Для issues:
- state=all
- per_page=100
- sort=created
- direction=asc
- без фильтра since
- переход по Link rel="next" до последней страницы

Нельзя обрывать пагинацию и считать такую загрузку успешной.
Если требуется защитный лимит страниц, его превышение означает ошибку.

Комментарии, события, timeline, отдельные детали PR и история
предыдущих состояний из GitHub в первую версию не входят.

## stg.load_batches

Одна строка соответствует одному логическому запуску DAG.

Поля:
- batch_id: UUID, первичный ключ.
- dag_id: TEXT.
- run_id: TEXT, идентификатор запуска Airflow.
- status: TEXT, running / success / failed.
- started_at: TIMESTAMPTZ, начало загрузки.
- finished_at: TIMESTAMPTZ, завершение; NULL для running.
- expected_repository_count: INTEGER.
- error_message: TEXT, безопасное описание ошибки без секретов.

Пара (dag_id, run_id) уникальна.
- started_at: TIMESTAMPTZ.
Повтор задачи внутри того же запуска использует прежний batch_id.
Новый запуск DAG получает новый batch_id.

Временные значения хранятся как TIMESTAMPTZ, рабочая зона UTC.

## stg.repository_loads

Одна строка на репозиторий внутри батча.

Поля:
- batch_id: UUID, ссылка на load_batches.
- repository_full_name: TEXT, имя из конфигурации.
- status: TEXT, running / success / failed.
- finished_at: TIMESTAMPTZ.
- repository_record_count: INTEGER.
- issue_record_count: INTEGER, включая PR.
- issue_page_count: INTEGER.
- error_message: TEXT, без токенов и Authorization.

Первичный ключ: (batch_id, repository_full_name).

Ожидается одна запись репозитория.
Ноль issues допустим при успешном ответе API с пустым списком.


## stg.github_repositories_raw

Одна строка на репозиторий в батче.

Поля:
- batch_id: UUID.
- repository_full_name: TEXT.
- payload: JSONB, полный объект API.
- loaded_at: TIMESTAMPTZ, момент сохранения.
- source_url: TEXT, URL запроса без секретов.
- http_status: INTEGER, 200 для сохраненного ответа.

Первичный ключ: (batch_id, repository_full_name).
Ссылка на соответствующую строку repository_loads.

## stg.github_issues_raw

Одна строка на элемент списка issues в батче.
Поля:
- batch_id: UUID.
- repository_full_name: TEXT.
- github_issue_id: BIGINT, поле id из объекта API.
- payload: JSONB, полный объект элемента.
- loaded_at: TIMESTAMPTZ, момент сохранения.
- source_url: TEXT, URL страницы без секретов.
- http_status: INTEGER, 200 для сохраненного ответа.


Первичный ключ:
(batch_id, repository_full_name, github_issue_id).

Ссылка на соответствующую строку repository_loads.

github_issue_id — технический ключ дедупликации.
Остальные бизнес-поля извлекаются в DDS.
Поле number не используется как глобальный идентификатор issue.

## Сохранность исходных данных

payload сохраняет все поля полученного объекта.
Не удаляются body, labels, assignees, user, pull_request и другие поля.
JSONB не гарантирует исходное текстовое форматирование JSON.
Ответы API со статусами ошибок не сохраняются как бизнес-объекты.
Ошибка фиксируется в метаданных загрузки.

## Повторы и атомарность


Повтор задачи не должен создавать дубликаты в том же батче.

Успешно загруженный репозиторий в том же батче пропускается.
Для незавершенного репозитория загрузка повторяется целиком.

Публикация сырых строк одного репозитория и перевод его в success
выполняются одной транзакцией после получения всех страниц.
Во время HTTP-запросов транзакция записи в DWH не удерживается.
При ошибке записи транзакция откатывается.
Статус failed записывается отдельной транзакцией.

Успешные батчи и их сырые данные не перезаписываются.
Автоматическая очистка STG в первую версию не входит.

## Критерий успеха батча

Батч получает success только если:

- Загружены все репозитории из конфигурации данного запуска.
- Все соответствующие repository_loads имеют status=success.
- Получен JSON каждого репозитория.
- Для каждого репозитория полностью завершена пагинация issues.
- Проверены фактические количества сохраненных строк.

Если хотя бы один репозиторий не загружен, батч не может быть success.
Незавершенные после аварии батчи running не используются DDS.


DDS читает только батчи со status=success.
running и failed не используются даже при наличии сырых строк.


Обрабатываются все еще не обработанные успешные батчи,
а не только последний.

Порядок обработки: started_at, batch_id.
DAG загрузки работает с max_active_runs=1.

DDS самостоятельно хранит отметки обработанных batch_id.
Успешные пустые списки issues не считаются ошибкой.

Отсутствие issue в следующем батче само по себе
не трактуется как подтвержденное удаление.

## Ограничения аналитики
Issues endpoint содержит issues и PR.
DDS различает их по наличию поля pull_request.

issue_record_count включает оба типа.
Метрика количества именно issues требует фильтрации в DDS/CDM.

SCD2 отражает состояния, наблюдавшиеся при наших загрузках.
## Передача команде
Пропущенные изменения между запусками восстановить нельзя.

API не предоставляет атомарный снимок всех страниц:
данные могут изменяться во время обхода.
Полная пагинация означает завершенный обход,
а не строгий снимок источника на одну временную точку.

История stars и forks начинается с первого нашего снимка.
Получить их прошлую динамику из текущих счетчиков нельзя.


Код и контракт передаются через Git.
Данные передаются отдельным экспортом PostgreSQL
с инструкцией восстановления.

.env, GitHub-токен и реальные пароли не передаются через Git.
